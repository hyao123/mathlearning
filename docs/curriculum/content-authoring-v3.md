# V3 课程内容编写、版本与兼容性

本说明面向提交 V3 课程内容的作者与负责激活、发布及回归验证的维护者。它定义内容更新如何与既有学习进度共存；内容升级不是重置学习档案的理由。

## 内容批次与稳定身份

一份可激活的 V3 内容批次以稳定的章节/模块槽位（`chapterId` + `moduleId`）定位课程主题，并携带一个非空的 `contentVersion`。批次中的题目替换的是该稳定槽位的内容，而不是创建新的关卡身份。

- 既有 `levelId`、`question.id` 和奖励/领取账本的键保持不变；不要为一次内容修订改写这些 ID。
- 批次必须引用已注册的课程主题和兼容性槽位。未注册、重复或不兼容的章节/模块组合不能激活。
- 只有通过审核并被注册为活动内容的 V3 批次会把其 `contentVersion` 编译到对应关卡；旧版关卡继续保持原有形状，不增加版本字段。

## 学习者状态与重玩

地图根据当前关卡内容和该关卡最近完成记录的版本派生三种状态：

| 状态 | 条件 | 学习者可见行为 |
| --- | --- | --- |
| `unplayed` | 没有完成记录 | 按正常首玩流程显示。 |
| `current` | 当前关卡没有版本，或记录的 `contentVersion` 与当前关卡一致 | 显示既有的完成/星级状态。 |
| `updated` | 当前 V3 关卡有版本，且完成记录没有版本或版本不同 | 显示“内容已更新 · 可重新挑战”，关卡仍保持已解锁且可点击。 |

`updated` 不是未解锁状态，也不会抹去历史完成。学习者可重玩更新后的 10 题内容；结算时保留历史与本次结算中较高的星级，即记录的 `starCount` 取最大值。

更新后的重玩也不得重复发放首通资源。固定奖励领取账本、尝试账本、背包和其他既有奖励记录必须原样保留；已领取的首次通关奖励继续被识别为已领取。

## 存档兼容性

版本字段只会为有效的 V3 运行和完成记录持久化：

- 启动带 `contentVersion` 的 V3 关卡时，运行记录携带相同版本；完成后，该版本写入对应的关卡完成记录。
- 缺少 `contentVersion` 的旧完成记录仍是有效历史记录。它们会在当前 V3 内容激活后显示为 `updated`，而不是被自动当作已完成的新内容。
- 旧版关卡和旧版存档继续按原样读取，不要求补写版本字段。
- 恢复存档时，活动运行的版本必须与当前关卡版本完全一致。版本不匹配的活动运行会被丢弃并返回地图，避免在同一次运行中混用新旧题目。

## 作者激活清单

激活新的 V3 内容版本前，逐项确认：

- [ ] 每个章节/模块槽位恰好有 10 道 V3 题目。
- [ ] 章节/模块已注册到课程主题，并存在对应的兼容性槽位。
- [ ] 批次、题目质量和难度递进等全部自动化门禁均已通过。
- [ ] 批次附带状态为 `approved` 的审核清单（review manifest）。
- [ ] 审核清单中的每道题 `contentHash` 与待发布题目内容一致；内容有任何变动时，先更新哈希并重新审核。
- [ ] 批次使用新的、非空的 `contentVersion`；不得复用或回退活动版本。

## 发布检查

在提交和激活前，从仓库根目录运行下列检查。全部成功后，才可把审核通过的批次注册为活动版本：

```bash
npm test
npm run check
npm run validate:game
npm run validate:release
npm run test:game-ui
npm run build
git diff --check
```

其中 `npm test` 覆盖单元与回归测试，`npm run check` 检查语法，`npm run validate:game` 和 `npm run validate:release` 检查内容与严格发布门禁，`npm run test:game-ui` 验证学习者可见的更新/重玩行为，`npm run build` 验证可构建产物，`git diff --check` 防止提交空白错误。若任一命令失败，不得激活该内容版本；记录完整输出并先修复或明确环境阻塞原因。
