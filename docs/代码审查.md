### 问题清单

#### 🔴 严重问题

**问题1：生产包体积门禁已失败**
- 位置：`scripts/check-bundle-size.js:7-15`、`src/game-main.js:50-78,112`
- 问题：构建后 JS gzip 为 167423 bytes，超过 160 KiB 门禁；启动时还会顺序加载全部章节题包并编译 720 道题。
- 风险：发布检查无法通过，后续第七章继续加入后首屏体积和启动时间会持续恶化。
- 建议：改为“章节元数据首屏加载、当前章节题包按需加载、进入关卡时再编译题目”；同时把 `build && check:bundle` 合并为单一发布命令，避免检查旧 `dist`。

**问题2：战役存档与背包分开写入，存在部分写入导致物品回退/丢失**
- 位置：`game/gameApp.js:463-487`、`game/campaignModel.js:22-28`、`game/storageAdapter.js:105-127`
- 问题：一次答题分别写入 `math-quest-campaign-v2` 和 `math-quest-inventory-v1`；若一个写成功、另一个失败，启动时 `createCampaign` 会优先采用非空背包并覆盖章节状态中的背包。
- 风险：浏览器隐私模式、存储空间不足或升级迁移时，进度与物品可能不一致，直接违反“背包升级不丢失”的核心要求。
- 建议：建立带 `revision` 的单一存档信封，或采用 journal/commit 标记；加载时按 revision 原子恢复，并提供旧双键存档的一次性迁移。

**问题3：人工审核门禁可被默认流程绕过，且可批量伪造为已审核**
- 位置：`scripts/validate-game-content.js:45-52,161`、`scripts/generate-human-review-template.js:11-23`
- 问题：只有设置 `REQUIRE_HUMAN_REVIEW=1` 才校验审核记录；`npm run validate:game` 默认不启用该门禁，`--approve` 会直接把全部题目六项评分设为 1。
- 风险：720 道题可能在没有逐题课程审核的情况下进入“approved”状态，故事、答案解释和难度问题无法被发布流程拦截。
- 建议：新增 `npm run validate:release` 强制严格审核；移除或限制批量 `--approve`，审核状态必须来自真实审核记录，并校验 reviewer、时间和题目版本。

#### 🟡 建议修改

**问题4：章节题库注册仍是手工分支，尚未真正声明式扩展**
- 位置：`game/chapterBuilder.js:1-20,82-90,162-169`、`src/game-main.js:50-90`
- 问题：新增章节仍需同时修改多个 import、`NATIVE_CHAPTER_MODULES`、`ALL_SUPPLEMENTAL_QUESTIONS` 和运行时 loader；题包数量还通过 `chapterId === "chapter-03"` 等特殊条件判断。
- 建议：建立统一 `chapterRegistry`，由章节配置声明 metadata、question loader、题数、奖励、项目、故事和审核 manifest；builder 只消费注册表。

**问题5：奖励存在两套来源，未来容易出现预览与实际发放不一致**
- 位置：`game/chapterExpansionData.js:55-67`、`game/levelRewardConfig.js:37-68`、`game/rewardEconomy.js:77-85`
- 问题：`CHAPTER_THEMES.rewardPlans` 按 `chapterId + slot` 描述一套奖励，真实发放则使用 `levelId + questionSlot` 的 `LevelRewardConfig`；其中还有未使用的旧 `rollRewardForSlot`/`getExpectedRewardPlans` 路径。
- 建议：统一为一个 `RewardTrack` 接口，以关卡和题位为唯一键；预览、结算、模拟、校验全部调用同一解析器，并删除旧兼容路径或明确标记 deprecated。

**问题6：故事和战术复盘结构通过校验，但语义深度仍偏模板化**
- 位置：`game/chapterQualityProfiles.js:172-204`、`game/storyMissionModel.js:11-22`
- 问题：大量题目共用“观察记录/结果核对/易错提醒”模板，复盘步骤主要只是把单段 explanation 包装成步骤；结构校验不能证明推导过程真的对应答案。
- 建议：为每个专题建立可执行的 `solutionReview` 步骤类型（观察、列式、计算、验算），增加答案与解释的一致性校验，并对每章抽样进行课程负责人审阅。

**问题7：视觉资源虽然有覆盖，但“延迟加载”目前主要是标记，不是真正减小首屏 JS**
- 位置：`game/itemVisuals.js:186-208,250-285`
- 问题：大量 SVG data URI 和 265 个物品 ID 直接嵌入 JS；`preloadPriority`/`loading` 不会阻止这些字符串进入初始 bundle。
- 建议：视觉清单改为生成式 manifest，普通物品使用外部 WebP/精灵图或按章节拆分资源；最终工程与当前奖励优先加载，其余真正按需请求。

**问题8：恢复挑战存档校验不如普通关卡严格**
- 位置：`game/challengeModel.js:90-115`、`game/progressionModel.js:545-553`
- 问题：恢复挑战 hydrate 时未完整校验 `correctCount + skippedCount`、已奖励题号与当前题位的关系，也未重新计算目标材料和奖励交易合法性。
- 建议：复用普通关卡的 run schema 校验器，恢复时重新计算 target、交易摘要和计数；增加损坏存档、重复提交和半写入恢复测试。
